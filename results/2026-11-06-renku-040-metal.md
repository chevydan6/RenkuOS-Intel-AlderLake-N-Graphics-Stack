# Renku-040 physical laptop test

The user requested an actual test of the new build on the N100 laptop. The
kernel driver and accelerant from bundle `renku-040` were installed on the
separate RenkuTest USB volume; the prior files were backed up on the USB and
on the development host. The first reboot exposed a second older driver copy
under `/boot/home/config/non-packaged`, which took precedence. Its old file was
also backed up and replaced, followed by a second reboot.

The laptop returned on SSH from `/dev/disk/usb/0/0/1`. The new kernel driver was
verified by its version-2 shared-layout ioctl, which returned the expected
structure size 2312, PCI ID `8086:46d1`, revision 0, VBT BDB 251 and child
record size 39. The driver and accelerant hashes match the validated bundle.
The boot log records HDMI G EDID detection and the corrected DDI register
mapping. This does not establish that the display has a picture. The new
experimental HDMI output sequence is not connected to modesetting and did not
execute on the GPU. There is no evidence of hardware graphics acceleration.

Using a read-only copy of the driver's shared information, the new firmware
validation helper initially rejected the hardware because `got_vbt` is false.
Source review shows that this flag reflects whether panel timing was found,
not whether child records were parsed. Patch 42 removes that unrelated
condition while retaining the version, record-size, device and uniqueness
checks. Compiled as a standalone read-only diagnostic on the laptop, the fixed
helper accepts the actual data and reports TC2, preset 0, no lane reversal and
a 38.4 MHz reference. This was not a GPU register programming test. The
current running bundle is still `renku-040`; patch 42 has not been installed
as a new system build.

NanoKVM was then queried during this boot. Its capture status reported
`state=0` and `now_fps=0`; its authenticated MJPEG stream produced no HTTP
response or frame before the 15-second read timeout. The configured stream
type was H.264, so the MJPEG result alone does not establish the signal state.
No picture was captured or verified; this observation does not distinguish
an absent HDMI signal from a NanoKVM capture or stream configuration issue.
