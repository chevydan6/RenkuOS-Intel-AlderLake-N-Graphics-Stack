# After the first native N100 GPU copy: development research

2026-11-14. Research and recommendations, not implementation or a new physical test. Source snapshot: native continuation [copy checkpoint 7f32216](https://github.com/chevydan6/haiku-intel-gpu/commit/7f32216b74e659eb7a8ff01a7498d5977849c79c); RenkuOS Source [4799bb5a188c4bb6bbef967287640cc21a061a0d](https://github.com/RenkuOS/Source/tree/4799bb5a188c4bb6bbef967287640cc21a061a0d). Check current branch and target state again before implementing; this note is not permission to run a new physical trial.

## What is proven and what is not

[Native handoff](../../NATIVE_GPU_HANDOFF.md), [sample source](../../experimental/native-gpu/gpu_copy_sample.cpp) and [execution005 evidence](../../experimental/native-gpu/evidence/native-copy-005/README.md) document a real 4 KiB BCS copy between private PPGTT pages: all 1024 dwords matched, nonce/complement and ordered breadcrumb matched, fresh CSB activation and idle-completion events were accepted, no reported fault, forcewake was released and app_server remained alive. It is one execution, not a throughput result or a test of resource reclamation, repeated submissions, client concurrency, shader execution, or recovery from a hung published request.

[NativeExecution.inc](../../experimental/native-gpu/NativeExecution.inc) exposes a report-only, kernel-generated fixed workload. The attempt and its memory are intentionally retained until reboot; a resident owner holds the execution state. It uses an explicit limited direct-DMA admission that requires observed VT-d translation disabled, owned PPGTT/scratch tables and data pages, global cache policy setup and an x86-wide wbinvd visibility operation. [CopyRequestImage.h](../../experimental/native-gpu/CopyRequestImage.h) uses two 4 KiB, 32-bit linear surfaces, a single 1024×1 copy and fixed uncached MOCS. [LinearCopy.h](../../experimental/gen12/LinearCopy.h) rejects overlapping VA allocations and same-surface copies. These constraints define the first engineering work; do not treat them as a general buffer, DMA or display interface.

The physical run is sufficient to proceed; a standalone N100 PRM, a complete LinuxKPI port, a new scheduler, broad test matrices, and repeating the one-shot proof are not prerequisites. Preserve the native approach, existing helpers, licenses, display state and ownership model.

## Recommended path and alternatives

**Recommendation:** first make the existing fixed BCS operation repeatable in a controlled resident service, then add a narrow copy interface with owned buffers, measure an actual application and investigate desktop presentation in parallel as a source-only study. Keep one GPU request in flight initially. Retain the polling-based completion model until measurements or a real integration requirement justify interrupts. This is the shortest route from a single proof to useful, diagnosable GPU work while preserving the established approach.

Two other credible paths:

1. **Desktop-first:** immediately wire screen-copy accelerant hooks to BCS. This promises visible output sooner but the pinned app_server uses a CPU malloc-backed RGBA back buffer and does not look up the old blit hooks in the inspected interface. The current linear builder also rejects overlapping copies, which screen scrolling frequently needs. A hook alone therefore does not establish desktop acceleration.
2. **3D-first:** target Mesa Iris/OpenGL immediately. This aims at games and shaders directly but requires a substantially richer buffer, context, synchronization and submission interface, render engine initialization, compiler/runtime integration and a native winsys. It is a research track after the reusable foundation, not a replacement for it. Mesa describes [Iris, HGL and winsys layers](https://docs.mesa3d.org/sourcetree.html); this establishes components, not proof that upstream Iris can run unchanged on RenkuOS.

## Milestone 1 — repeatable trusted copy

Separate **once per device boot** setup from **per-request** setup without presuming the engine must be reset for every operation. Establish a serialized resident engine state machine: unavailable → ready → submitted → completed/retired → ready; an uncertain publication, failed deadline or lost ownership leads to failed/quarantined state. Keep request-owned pages, context and mappings referenced while hardware can still access them. Reuse already-allocated pages initially: replacing permanent per-boot retention with a bounded reusable pool can precede full public allocation/free. Track sequence plus reset generation to reject stale completion and distinguish a GPU operation that signalled an error from successful output.

On success, separately establish the breadcrumb, CSB transition/engine inactivity, CPU visibility and release of the request’s references. A breadcrumb alone is not proof that all context backing can be freed. On timeout stop accepting work, preserve diagnostic status, return a bounded error and quarantine uncertain backing. Do not report the fence successful or free/reuse memory merely because the client timed out. An engine reset and later recovery may be added only with its own checked completion and ownership contract; otherwise reboot remains the supported recovery. Prior reset-only success is not evidence that a hung published request is recovered safely.

**Focused acceptance:** several sequential copies in one boot using changing source patterns and destination poisoning, including a second request after the first, exact comparisons and existing CSB/fault evidence; reject concurrent submission or serialize it; report retained memory and maintain the desktop. Include one controlled pre-publication error path and a software-injected timeout/state transition without deliberately hanging the GPU. Do not infer success from a green CPU mock. Use the project physical lease/recovery procedure when a future physical run is authorized.

## Milestone 2 — buffer and copy interface

Introduce a private, versioned native service, not arbitrary user-supplied MMIO, physical addresses or GPU commands. A first interface can have create/close buffer handles, explicit CPU access transitions, submit-copy and wait/status; each handle is scoped to its client/owner and request holds references to its source/destination until retirement. A synchronous copy operation is acceptable for the first client; a sequence-bearing completion handle is useful if asynchronous work becomes necessary. Errors distinguish invalid arguments, unsupported format/overlap, busy, timeout, and device loss.

Start with a documented linear 32-bit non-overlapping rectangle. Validate buffer ownership and access, offsets, width/height, pitches, format, arithmetic overflow, bounds and GPU VA mappings before publishing any work. The sample's 1024×1 case is not evidence for every multi-row pitch or framebuffer format. Explicitly reject unsupported overlap or aliasing (including two handles to the same backing); a later overlap-capable path needs direction semantics and tests. Specify whether coordinates and dimensions are pixels or bytes. Keep the commands kernel-built. Test a few representative sizes, multi-row pitch and guards with exact CPU comparison. Client close while active must retain the backing until the request has retired or has been safely quarantined.

Keep the direct-DMA backend explicitly limited to the validated environment. General support for active VT-d needs a proper OS DMA mapping/IOMMU contract with returned device addresses, lifetime and unmapping; do not equate CPU physical addresses and GPU-visible DMA addresses. [Linux DMA mapping guide](https://docs.kernel.org/5.15/core-api/dma-api-howto.html) explains the conceptual distinction; it is a reference, not an instruction to import Linux APIs. Formalize the CPU→GPU and GPU→CPU visibility transitions before removing the current coarse wbinvd; optimize only after correctness and a platform-specific cache policy are established. Never assume a GPU virtual address is a CPU pointer.

## Milestone 3 — prove usefulness and choose desktop integration

Build one small native demonstration with repeated offscreen rectangular copies or a visible image update through an explicitly synchronized staging/presentation path. Compare byte-for-byte against CPU output. Measure end-to-end wall time, not just engine time: allocation/mapping, cache maintenance, submission, waiting and readback; test a few sizes including small UI rectangles and larger images. Compare a warm CPU memcpy/software baseline using the same data, and record CPU time, GPU timing if trustworthy, errors and memory footprint. The current wbinvd and per-operation overhead may dominate small copies. Keep results labeled by hardware, build and path.

Before promising desktop speedups, inspect the exact running RenkuOS app_server and measure its current back-to-front path. At the pinned source, [AccelerantHWInterface.cpp](https://github.com/RenkuOS/Source/blob/4799bb5a188c4bb6bbef967287640cc21a061a0d/src/servers/app/drawing/interface/local/AccelerantHWInterface.cpp#L636) allocates a MallocBuffer RGBA back buffer; [intel_extreme hooks](https://github.com/RenkuOS/Source/blob/4799bb5a188c4bb6bbef967287640cc21a061a0d/src/add-ons/accelerants/intel_extreme/hooks.cpp#L93) expose legacy engine and 2D hooks, but inspection of the pinned app_server interface found no lookup of B_SCREEN_TO_SCREEN_BLIT. These two facts imply a hook implementation alone is insufficient for normal desktop rendering. Verify actual build and the precise copy/conversion call path before choosing integration.

Possible integration experiments: a GPU-copy-capable staging buffer plus synchronized presentation for compatible damage rectangles, or a new offscreen/compositor interface that owns buffers and synchronizes CPU/GPU access. Existing CPU-rendered back buffer, color conversion, row pitch, dirty regions, overlap, scanout ownership and modeset need explicit handling. Benchmark each path; prefer CPU fallback for unsupported formats, small rectangles, errors and device unavailable. Never expose partially drawn or stale output as a success.

## Milestone 4 — GPU rendering and APIs

If accelerated applications or 3D desktop rendering are desired, take a separate render-engine milestone: native render context and workarounds, buffers and synchronization, a small known shader or render workload, readback verification and recovery. This is a new engine and capability beyond BCS copy. Study Mesa Iris for Gen8+ rendering, its Intel buffer management and kernel interfaces, HGL frontend and platform integration. Prototype feasibility against a pinned Mesa revision and the real native kernel interface; do not assume Gallium's conceptual winsys separation removes Iris's Linux DRM dependencies. OpenGL requires shader compilation, resource formats, context management and presentation; Vulkan adds its own driver/WSI and synchronization requirements. No API capability should be advertised before real conformance and application smoke checks.

## Lifecycle and scope decisions

- **Synchronization:** request status must distinguish successful completion, error and timeout; software fence completion with an error does not authorize freeing backing whose hardware ownership is uncertain. A request holds its own references independent of the client. [Linux DMA fence documentation](https://docs.kernel.org/6.8/driver-api/dma-buf.html) is useful design context, not a requirement to reproduce Linux.
- **Power and reset:** preserve the validated forcewake ledger and exclusive owner. Define which engine/global state is reinitialized after reset and how stale completions are invalidated. Suspend, resume, hot-unplug and unload are future lifecycle features; explicitly decline unsupported transitions rather than claim support.
- **Interrupts:** polling is appropriate for the first repeatable serialized path. Interrupt support later requires shared display IRQ coordination, safe handler/module lifetime, acknowledgement and a polling/timeout fallback.
- **Security/scope:** the first private service is kernel-built copies, not general GPU command submission to untrusted users. Arbitrary command buffers require a separate isolation and validation design.
- **Attribution:** retain file-level Intel/Linux origin, license notices and exact source pins. Do not restart the archived LinuxKPI port.

## Proposed immediate work package

1. Document the existing execution state and exact ownership boundaries; identify which retained objects can be safely reused after the observed completion and which require an additional retirement proof.
2. Refactor one fixed kernel-generated copy into serialized repeated submissions using the existing ownership, CSB and polling helpers. Keep unsupported failure states quarantined until reboot.
3. Run focused build checks and, in a coordinated future physical session, several changing-pattern copies in one boot with byte checks, completion records and desktop postcheck.
4. Add narrow owned-buffer rectangle operations only after the repeated path is stable; benchmark before committing to any app_server integration.

This roadmap is a recommendation, not evidence that any of these milestones have been implemented or tested.
