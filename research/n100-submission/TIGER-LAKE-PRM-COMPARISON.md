# Tiger Lake Xe-LP PRM compared with the N100 i915 path

2026-11-14. Documentation comparison only, no implementation or hardware changes. The comparison uses Linux commit [028ef9c96e96197026887c0f092424679298aae8](https://github.com/torvalds/linux/tree/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915). The [N100 GPU research](N100-UHD-GRAPHICS-RESEARCH.md) and [i915 map](INTEL-DOCUMENTATION-I915-MAP.md) provide background.

Tiger Lake and Alder Lake graphics share Xe-LP; the detailed Tiger Lake PRM is consequently useful evidence for the common GPU model. The comparisons below identify what was actually checked. Matching behavior in Linux and a related-platform manual is stronger than an isolated analogy, but it does not independently establish that every target-specific field, fuse, or workaround is identical.

## Submission queue and contexts — strong conceptual match

[Intel Tiger Lake Volume 8, IHD-OS-TGL-Vol 8-12.21, December 2021 revision 1.0, printed pp. 2–5](https://cdrdv2.intel.com/v1/dl/getcontent/703062#page=5), Scheduling and Execlists, says each engine has a context and ring, LRCA points to global graphics virtual memory, and the ring registers and page directory are initialized before submission. Printed p. 3 describes both cyclic ELSP writes and direct MMIO access to individual SQ entries; writing the SQ alone does not start execution, and Load samples it into the execution queue. The SQ persists after Load. Thus the manual is not limited to the old ELSP-only model: its direct SQ description is the relevant comparison for ELSQ.

Pinned Linux selects [SQ contents and control](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L3553) when HAS_LOGICAL_RING_ELSQ, [writes each descriptor low dword then high](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L723), [fills slots in descending order, clears unused ones and issues Load](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L905). The manual confirms the model and persistence; the particular software write order is established here by i915, not by the cited general PRM text. The [ADL-N PCI entry](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/i915_pci.c#L862) selects the device info that inherits ELSQ.

Volume 8 printed pp. 5–6 describes the per-process status page, ring context and engine context; PDPs set up PPGTT while the ring lives in global graphics address space. It describes restore-inhibit for first use and engine-specific context formats. Linux implements [Gen12 XCS offsets](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_lrc.c#L227), [initial image](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_lrc.c#L1016) and [ring/PPGTT register updates](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_lrc.c#L1537). The PRM's five-cacheline logical-ring description does not specify the total allocated backing or the extra Linux workaround pages: see [project context image design](CONTEXT-IMAGE-DESIGN.md).

## Status and ordering — important details

[Volume 8 printed pp. 7–10](https://cdrdv2.intel.com/v1/dl/getcontent/703062#page=10), Context Status, describes 64-bit switch records, idle context ID 0x7ff, a 12-entry circular buffer in the global hardware status page, a last-written pointer and masks which can suppress both report and interrupt. It distinguishes idle-to-active, active-to-idle, queue switch and preemption. A completion interpretation cannot simply equate every context switch with a finished request.

Linux [configures HWSP-backed CSB and Gen11+ size](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L3568), [parses the Gen12 format](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L1703) and [reads pointer before buffer with a read barrier](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L1814). Its [reset_csb_pointers](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L2805) sets the initial software index to the last entry so the next read starts at entry zero, initializes status and flushes the relevant range. The PRM's conceptual status layouts corroborate this approach; exact offset and field equivalence still requires comparing the register/structure volumes to the pinned definitions.

[Volume 8 printed pp. 53–55](https://cdrdv2.intel.com/v1/dl/getcontent/703062#page=57) distinguishes posted stores from non-posted post-sync MI_FLUSH_DW and lists operations that bring previous posted writes to a globally observable point. This helps explain why the Linux [Gen12 XCS breadcrumb emitter](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/gen8_engine_cs.c#L807) has an ordered flush/breadcrumb. GPU ordering alone does not settle CPU cache visibility, DMA mapping, or safe backing release.

## Cache and copy engine

[Intel Tiger Lake Volume 7, IHD-OS-TGL-Vol 7-12.21, December 2021 revision 1.0, printed p. 5](https://cdrdv2.intel.com/v1/dl/getcontent/703061#page=9), “Memory Object Control State on Cacheability”, describes MOCS selecting cache and memory behavior through programmable tables and distinguishes IA-compatible paging memory typing. Compare Linux's [MOCS selection](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_mocs.c#L454), [initialization](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_mocs.c#L666), and [Gen12 PTE encoding](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/gen8_ppgtt.c#L61). This volume alone does not provide a complete PAT, GGTT, IOMMU and TLB programming contract. Do not transfer its table addresses or policies blindly.

[Intel Tiger Lake Volume 10, IHD-OS-TGL-Vol 10-12.21, December 2021 revision 1.0](https://cdrdv2.intel.com/v1/dl/getcontent/705824), printed pp. 5–6 identifies copy-engine mode, context size, HWS and reset-control registers and describes blitter MI commands. It points to register definitions; it does not by itself establish Linux's full engine bring-up, forcewake or reset sequence. Linux's [engine initialization](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_engine_cs.c#L953), [execlists enable](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_execlists_submission.c#L2928) and [reset preparation](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/gpu/drm/i915/gt/intel_reset.c#L560) supply the software sequence and workarounds. The project [reset research](BCS-RESET-DESIGN.md) records additional checks and prior observed results.

## Outcome

Shared Xe-LP PRM text directly supports the general design of memory-backed logical contexts, MMIO submission queue plus Load, circular context status and ordered completion. It does not establish that the physical GPU is initialized, that the complete cache/translation contract has been met, or that every Tiger Lake register value and workaround applies unchanged. No new physical execution is claimed.
